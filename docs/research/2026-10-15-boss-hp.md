# Boss HP — what the game knows, and where Foe's numbers go wrong

Research only. It lays out options and leaves the choice to the operator. Nothing here changes code.

**Bottom line.**

- The game has an exact boss HP feed: varbits 6099/6100 and varp 1683.
- That feed is not always HP. Measured crowd data shows it carrying a shield (the Nightmare) or an armour pool (Zalcano).
- At the Gemstone Crab the bar is a timer. The wiki gives the crab's HP as ∞, and its bar drains over about 10 minutes whatever players do.
- Foe's `Current/max` text is wrong in two ways today:
  - **An invented number:** an HP figure printed for a bar that isn't HP. This affects the crab, shield and armour pools, and the per-player Moons.
  - **A wrong max:** the cache's base value printed for an HP pool that scales. Raids, the Nightmare, the Doom's delves and the awakened DT2 bosses all scale.
- Foe's `Percent` text is right to within rounding in both cases, because it is the bar's own fraction.
- The three candidate designs are in §4. Which numbers only an in-game probe can settle is in §5.

## 0. What Foe does today (the baseline every row below is judged against)

Read from the code on `main` at `e57e865` `[measured]`:

| Step | Code | Behaviour |
|---|---|---|
| Max HP | `SnapshotFactory.java:39-43` | `NPCComposition.getStats()[HITPOINTS]` of the **transformed** composition (`FoePlugin.java:587,594`). If that is ≤ 0, it falls back to `NPCManager.getHealth(npc.getId())`, which looks up the **untransformed** id (`FoePlugin.java:580-583,595`). NPCManager's table is fetched by RuneLite's `NpcInfoClient` (`NPCManager.java`, 1.13.1 sources). |
| Current HP | `HpEstimate.java:58-85` | The overhead bar's `ratio/scale` gives a range of HP values. Foe shows its midpoint. This is the inverse of the server formula quoted at `OpponentInfoOverlay.java:169-171`. |
| Exact HP | `HpTracker.java:131-196` | Counts `max − damage + heals` from hitsplats. The count is shown only while it lies inside the live bar's range. On a mismatch Foe falls back to the midpoint. A full or empty bar re-anchors the count. |
| Unhit | `SnapshotFactory.java:53` | No bar seen yet but max HP known: Foe shows the max alone (`300`). |
| Text | `FoeOverlay.java:481-505` | `Current/max` = `hp/max`. `Percent` = `round(100·hp/max)`, clamped to 1–99 while the bar is partial. Both need `max > 0`. |

Consequence. Every number Foe prints is the bar's fraction times a max taken from the cache. **If the bar is not HP, or the cache max is not this fight's max, the `Current/max` text is wrong.** `Percent` survives either case, because the max cancels out (`hp/max ≈ ratio/scale`).

**The Gemstone Crab, traced through that code** `[inferred from the code + the operator's in-game observation]`:

- **Where the 300 came from.** The overhead bar was live, and some source gave max 300: the cache stats or NPCManager. Which one is **unknown**. The wiki says hitpoints `∞` and its bucket row has no `hitpoints` field (`[measured]`: `wiki.py bucket "Gemstone Crab"` → `14779 | None | 160`). So that source and the wiki disagree.
- **Why 291.** The crab takes damage hitsplats while its bar barely moves, so the hitsplat count is rejected (`HpTracker.java:172-189`). Foe then shows the midpoint. `291` is the midpoint for, for example, scale 120 ratio 116 (range 290–292) or scale 50 ratio 48 (288–293). At scale 255, ratio 247 even resolves exactly to 291 (`[measured]`: HpEstimate's formula enumerated over the scales in a one-liner).
- **What each text showed.** `Percent`: `round(100·291/300)` = 97, the same as the HUD. `Current/max`: an HP claim for a creature that has none.

## 1. The boss HUD mechanism

### 1.1 The variables

Sources:

- **Names:** `runelite-api-1.13.1-sources.jar` (`gameval/VarbitID.java`, `gameval/VarPlayerID.java`) `[measured]`.
- **Bit layout and observed values:** the Weird Gloop varbit database (chisel), which records crowd-sourced value counts, not wiki text. URLs: `https://chisel.weirdgloop.org/varbs/display?varbit=N` and `?varplayer=N` `[documented]`.
- **What the client does with them:** decompiled client script `[proc,hp_hud_update]` (script 2103) from `github.com/Joshua-F/cs2-scripts` at commit `0753c45` (2025-02-03) `[measured: cloned and read]`.

**Caveat:** that dump is about 20 months older than today's client, so the script may have changed since. `ScriptID.HP_HUD_UPDATE = 2103` in the 1.13.1 API agrees with the dump's `// 2103` header `[measured]`.

**Exact or scaled? Exact numbers in pool units, but the pool is not always HP.** The evidence:

- **The script prints the raw values** `[measured: hp_hud_update]`:

  ```
  def_string $text1 = "<tostring(%varbit6099)> / <tostring(%varbit6100)>";
  %varbit6100 = ~max(%varbit6100, 1);
  if (%varbit14708 = 1) { $int13 = ~minmax(0, 100, scale(%varbit6099, %varbit6100, 100)); $text1 = "<tostring($int13)>%"; }
  ```

  So the game prints `cur / base`, or with the percent option `floor(100·cur/base)%`. It never applies its own scale.
  **Side effect:** the client writes `6100 := max(6100, 1)` while the HUD is up. A reader must not trust `6100 == 1`.
- **Base values equal the bosses' wiki HP** `[documented chisel]`:
  - Galvek's 1200 appears 417 times, the same count as Galvek's id 8095 in varp 1683.
  - The Corrupted Hunllef has 1000 and the Crystalline Hunllef 600, matching their wiki HP.
- **Base values also take shield and armour pools** `[documented chisel, varbit 6100 change table]`:
  - `300 → 1000` 2,947 times and `1000 → 300` 1,929 times. Zalcano is armoured at 300 and weakened at 1000 (https://oldschool.runescape.wiki/w/Zalcano). Varp 1683 flips `9049 ↔ 9050` 2,947 / 1,929 times, the same counts.
  - Values 2000, 2200, … 9800 in steps of 200, then `→ 2400`. The Nightmare's shield is "2,000 … caps at 19,600", plus 200 per player over five. Her HP is 2400 (https://oldschool.runescape.wiki/w/The_Nightmare).
  - **So during the Nightmare's shield phase the HUD shows the shield as `cur / base`.**
- **RuneLite treats them as HP.** `OpponentInfoPlugin.java:203-213` reads 6099/6100 as current/max and rewrites the widget as a percent `[measured]`.

### 1.2 How RuneLite's Opponent Info uses them (1.13.1 sources, `[measured]`)

- `OpponentInfoOverlay.java:141-146`: *"The in-game hp hud is more accurate than our overlay and duplicates all of the information on it, so hide ours if it is visible."*
- `OpponentInfoOverlay.java:226-236`, the test for "HUD is up for this opponent":
  ```java
  boolean settingEnabled = client.getVarbitValue(VarbitID.HPBAR_HUD_BOSS_DISABLED) == 0;   // :228
  int opponentId = client.getVarpValue(VarPlayerID.HPBAR_HUD_NPC);                         // :231
  return opponentId != -1 && npc.getComposition() != null && opponentId == npc.getComposition().getId(); // :233
  ```
- `OpponentInfoPlugin.java:183-189`: hooks `ScriptPostFired` for script 2103.
- `OpponentInfoPlugin.java:191-219`: reads 6099/6100 and rewrites `HpbarHud.HP_BAR_TEXT` to a percent. The javadoc at `:192-193` says: *"This health bar is used in CoX, ToA, Gauntlet, quest bosses, etc. It is not used in ToB, which has its own."*
- `ZalcanoPlugin.java:149-162,273-277`: uses a `VarbitChanged` on varp 1683 to detect "in the cavern" (`npcId == ZALCANO_WEAKENED || npcId == ZALCANO`). At `:260-270` it counts orange hitsplats (`DAMAGE_*_ORANGE`) as **shield** damage, separate from health.

### 1.3 Does the feed arrive when the HUD is disabled?

**Unknown.** What is known `[measured]`:

- In the 2025 script dump, nothing reads varbit 12389 except the settings toggle and getter (`grep -l varbit12389` → `settings_boss_health_overlay`, `settings_get_toggle`). The HUD scripts themselves never test it.
- So the server decides what happens when the setting is off. Two possibilities: it doesn't open interface 303, or it doesn't send varp 1682/1683 at all. The dump can't tell these apart.
- RuneLite tests 12389 *before* trusting 1683 (`OpponentInfoOverlay.java:228`). That fits either behaviour.

Open question §5 Q1.

### 1.4 How the HUD target relates to Foe's target

- **Matched by NPC type id, never by NPC index.** Varp 1683 holds a type id (§1.1). RuneLite compares it with `npc.getComposition().getId()`, the untransformed composition (`:233`).
- **It follows form changes.** The chisel change table shows 1683 moving straight between a boss's forms `[documented chisel]`:
  - Zalcano `9049 ↔ 9050`
  - Crystalline Hunllef `9021 → 9022 → 9023`
  - Galvek `8095 → 8097 → 8096 → 8098`
  - The Nightmare `9432 → 9425`, `9427 → 9430`
  - Vanstrom Klause `9569 → 9570 → 9571/9572`

  Whether 1683 matches `getId()`, `getComposition().getId()` or `getTransformedComposition().getId()` when they differ is **unknown** (§5 Q3).
- **Several NPCs.**
  - One varp holds one type id. If two NPCs share that id, the HUD can't say which instance it means. A by-id match would claim both.
  - CoX's changelog says *"For the Vanguards, the HUD will show each of their healthbars individually"* (https://oldschool.runescape.wiki/w/Chambers_of_Xeric, 18 June 2020). The three Vanguards have different ids (7527/7528/7529, `bucket.txt`), but 1683 is a single varp. How three bars are fed is **unknown** (§5 Q6).
- **Set and cleared.** Chisel shows 1683 going `-1 → id` at the start of a fight and `id → -1` at the end, and 6100 going `0 → base` and `base → 0`. What triggers each one (first hit, entering the arena, death, leaving, logout) is **unknown** (§5 Q5).

### 1.5 `HPBAR_HUD_HP_1` / `_2` and the thresholds

These are **markers on one bar, not extra bars**. From the script (`[measured]`):

- Each of 10338, 10339, 10340 and 10341 is drawn when it is > 0 and ≤ base + 1.
- Its position is `scale(v − 1, base, width)` from the left. 10339 (upper threshold) is measured from the right.
- The interface has matching components: `HpbarHud.HP_BAR_1`, `HP_BAR_2`, `HEALTH_BAR_LOWER_THRESHOLD` and `HEALTH_BAR_UPPER_THRESHOLD` (`InterfaceID.java:10847-10850`) `[measured]`. Mapping the script's arguments to those names is `[assumed]`.
- They would suit phase lines on a segmented boss (for example 75/50/25%). **Which bosses set them is unknown.** Chisel lists no observed values for 10338 or 10340 `[documented]`.

## 2. Boss catalogue

**How to read it.**

- **HP** is from the wiki's `infobox_monster` bucket, per NPC id `[measured]`. The query is `uv run python3 wiki.py bucket <page>`, using the same bucket and API as `WikiFetch.java`, and the output is saved in `bucket.txt`.
- Every other cell is `[documented]` from the page in the **Src** column (`https://oldschool.runescape.wiki/w/<Src>`) unless it is tagged.
- **HUD** is "yes" only when a source says so:
  - `S` = wiki Settings page
  - `C` = CoX changelog
  - `RL` = RuneLite javadoc
  - `ch` = chisel 1683 values
  - `op` = operator in game
  - `w` = the boss's own page

  Otherwise it is "unknown".
- **Scaled**: `scaledhp=Yes` is the infobox flag. A scan of all pages fetched for this note found 22 pages with it `[measured]`. The bucket has no such field, as its schema shows `[measured]` (`Bucket:Infobox_monster?action=raw`).

## 3. What Foe shows today, and where that's wrong

Failure classes (the first two break the rule "never show a number it doesn't know"):

| Code | Name | What the player sees |
|---|---|---|
| **INV** | invented number | `Current/max` prints an HP figure for a bar that is a timer, a shield or a per-player pool |
| **MAX** | wrong max | the max is the cache's base, not this fight's. Current is then the bar's fraction × the wrong max: a number in the wrong units |
| **PHS** | stale across a phase | the hitsplat count and remembered bar carry over a form change. The bar check rejects them and Foe shows the midpoint until a full or empty bar re-anchors. **Self-correcting.** |
| **HEAL** | unseen heals | heals with no `HEAL` hitsplat (siphon, healers, regen, resets): the count is rejected and Foe shows the midpoint. **Safe.** |
| **MULTI** | one of several | the fight's HP is spread over NPCs (Vanguards, Olm, Dusk/Dawn), but Foe shows one target. Honest for that NPC |
| **OK** | fixed single pool | estimate or exact HP, correct |

Each row's reasoning is the §0 code path applied to the §2 facts. Rows that rest on "cache HP = wiki HP" carry `[assumed]`. The crab shows that assumption can fail. Whether the overhead bar shows a shield or the HP during a shield phase is **unknown** for every boss.

## 4. Candidate designs (no choice made)

### A. Prefer the HUD feed when it is about Foe's target

When `varp1683 == target.getComposition().getId()` and `6100 > 1`, Foe would show `6099/6100` as exact current/max and its percent. Otherwise it would behave as today. Optional: also require `12389 == 0` (as RuneLite does), or not, depending on §5 Q1.

| | |
|---|---|
| **Fixes** | **MAX** wherever the HUD runs: CoX (which has the HUD), ToA, the Nightmare, the Doom, the Hunllefs. The HUD's base is the fight's real, scaled value (§1.1: the Nightmare's shield arrives in per-player 200 steps). It also gives exact current HP where the overhead bar only gives a range. The source is the one RuneLite's own overlay defers to. |
| **Can't fix** | **INV** when the HUD itself shows a non-HP pool: the crab's timer (if 6100 is 300 there), the Nightmare's shield, Zalcano's armour. The feed carries no "this is a shield" flag. Hints exist: a 1683 id change, a name param, a blue bar (Doom), all **unknown** as signals. Other gaps: ToB and Inferno, which use their own HUDs; bosses with no HUD (the DT2 awakened modes, unless they have one, unknown); two NPCs sharing one id; and the setting-off case, if values stop arriving. |
| **Test** | A pure function `(targetId, varp1683, v6099, v6100, v12389) → (hp, max, source)`, with fixtures from probe lines (§5): crab, Zalcano 300 ↔ 1000, Nightmare 2000 → 2400, a mismatched id, `6100 == 1`. Replay a recorded probe log through it, tick by tick, and assert the shown text at each tick. Mutant: drop the id check, and a fixture with a different NPC's HUD must fail. |

### B. Percent-only when Foe can't vouch for the max

Foe would keep the bar and the `%`, and drop `Current/max` and `Current` to `Percent`, for any target where the max is in doubt. Possible detectors, each usable alone:

1. **Hitsplats vs bar.** Damage hitsplats summing to more than the bar's resolution land while `ratio` doesn't move, over N ticks. Then the bar is not HP (crab, invulnerable phases). Generic, and needs no list.
2. **HUD disagrees with the cache.** The HUD names the target and `6100 ≠ cache max`. Then the cache max is wrong for this fight.
3. **The wiki says so.** The infobox has `scaledhp=Yes` or hitpoints `∞`. This needs a generated table, as in design C.

| | |
|---|---|
| **Fixes** | **INV** and **MAX** become an honest percent, everywhere a detector fires. It keeps the rule "never a number it doesn't know" by showing less. |
| **Can't fix** | It gives no exact HP: it removes numbers rather than finding them. Detector 1 needs a warm-up, so the first ticks still show `x/max`, and it can misfire on high-defence bosses where many hits are 0s (a 0 has `amount ≤ 0` and is ignored, `HpTracker.java:98`). The timer reading is itself honest in percent: the crab's 97% is true about the bar, but it is time, not health. |
| **Test** | Unit fixtures: a sequence of hitsplats with a frozen ratio switches to percent after N; a moving ratio doesn't. Replay a crab probe log, then a normal-monster log as the control: same code, opposite answer, both in one test. Mutant: N = ∞, and the crab fixture must fail. |

### C. A per-boss exception table, bundled like the weakness table

A dev-run generator, like `WikiFetch` (addendum 7), would emit `npcId → kind`. Kinds: `timer` (crab), `shield-pool` (Zalcano 9049, the Nightmare's shield, Phosani's), `scaled` (`scaledhp=Yes`: 22 pages, §2), `mode-varies` (awakened DT2, the Doom's delves), and `fixed`. Foe would act on the kind: percent-only for `timer` and `scaled`, or "HUD only" (A) for `scaled`.

| | |
|---|---|
| **Fixes** | Every listed case, from the first tick, deterministically, with no warm-up. |
| **Can't fix** | New content until the next regeneration. Cases the wiki doesn't state: the crab's 300 appears only as trivia, "Nex scaling" isn't stated at all, and the HUD flags would need hand entries. Two warnings: `scaledhp` is a **template parameter, not a bucket field** (the bucket schema has no such key `[measured]`), so the generator would have to parse wikitext; and a wrong entry persists until it is regenerated. |
| **Test** | A generator test against the committed JSONL, like the weakness table, and a corpus test that every `scaledhp=Yes` page yields an entry. Runtime fixtures: a table hit gives percent and a table miss gives today's behaviour. Mutant: delete the crab row, and its fixture must fail. |

The options combine. A gives exactness where the HUD exists. B is the generic safety net. C covers what the HUD and the detector cannot name. A and B together need no maintained data. C is the only one that can label a shield or a timer before any tick has run.
